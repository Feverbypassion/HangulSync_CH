# 이슈 03 — 재설치로 Keychain 허용 창이 뜨고, 읽기에 실패하면 신원 키가 조용히 새로 만들어진다

| 항목 | 내용 |
|---|---|
| 상태 | 실제로 발생·해결(재페어링). **코드 결함은 아직 수정하지 않음** |
| 발견 | 2026-11-06, 새 빌드를 `/Applications`에 설치한 직후 |
| 종류 | 기존 코드의 결함(업스트림에도 같은 코드) + ad-hoc 서명 빌드의 설치 절차 문제 |
| 심각도 | 중간 — 앱은 정상처럼 보이지만 동기화가 전혀 되지 않음. 데이터 손실·보안 사고는 없음 |
| 영향 범위 | 서명이 바뀌는 빌드를 재설치할 때, Keychain 허용 창을 거부·취소한 경우 |
| 관련 | [진행 기록 05](../progress/05-installation-and-field-test.md), 이슈 [02](02-direct-connection-lacks-peer-authentication.md)(신뢰 판정) |

## 1. 한 줄 요약

`SecureIdentity.loadOrCreate()`는 Keychain에서 키를 **읽지 못하면 이유를 구분하지 않고 새 키를 만들어 덮어쓴다.**
새 빌드를 설치하면 서명이 바뀌어 Keychain 허용 창이 뜨는데, 그중 하나가 승인되지 않으면 이 Mac의 신원(deviceID)이 바뀌고,
상대 Mac은 바뀐 ID를 신뢰하지 않아 동기화가 멈춘다. 재페어링이 필요하다.

## 3. 확인한 사실

| # | 사실 | 확인 방법 |
|---|---|---|
| F1 | 위 표의 창 표시·승인·거부 순서와 시각 | **실측** — 통합 로그(`securityd`, `secd`) |
| F2 | 신원은 존재했다(없지 않았다). Bonjour 서비스 이름의 접미사가 SHA-256 형태(소문자 16진수)이고, UUID 대체값(`DeviceID` 설정)은 저장되지 않음 | **실측** — `dns-sd`, `defaults` |
| F3 | 원격 Mac의 신뢰 목록에는 항목이 하나뿐이고, 그 ID의 앞 8자리가 이 Mac의 **현재 ID 앞 8자리와 다름** | **실측** — 사용자가 원격 Mac에서 `defaults read`로 확인 |
| F4 | 원격 앱은 구버전(Tailscale 경로 문자열이 바이너리에 있음) | **실측** — 사용자가 원격 Mac에서 확인 |
| F5 | 이 Mac → 원격으로 직접 연결은 있었고, 약 9분 동안 송신은 4.9KB인데 수신은 201바이트(원격 hello 1개 크기)뿐이었음 | **실측** — `netstat -anv` |
| F6 | 같은 빌드를 재실행하면 창이 1번만 뜨고, **"항상 허용"** 승인 뒤에는 partition 불일치도 `update` 호출도 없었으며 ID가 유지됨 | **실측** — 재실행 전후 로그, Bonjour 접미사, 항목 수정 시각 |
| F7 | 읽기 실패와 "항목 없음"을 구분하지 않는 코드 | **코드** — `SecureIdentity.swift:17-25` |

**추론(직접 증명은 못 함):** `update` 호출이 있었다는 것은 `readKey()`가 `nil`을 반환해 새 키 생성·저장 경로로 갔다는 뜻이다.
그 뒤 신원이 존재했으므로(F2) 저장이 성공했고, 따라서 **키가 새로 만들어졌다.** F3이 이를 뒷받침한다.
이 Mac에서는 비밀키를 읽을 수 없어(읽으면 다시 창이 뜸) 옛 키와 직접 비교하지는 못했다. 옛 ID 자체도 원격 Mac의 기록으로만 알 수 있었다.

## 4. 원인 분석 (코드)

`Sources/HangulSync/SecureIdentity.swift` (커밋 `65758f1` 기준):

- `:17-25` `loadOrCreate()` — `readKey()`가 데이터를 주면 사용하고, 아니면 곧바로 `Curve25519.KeyAgreement.PrivateKey()`를 만들어 `saveKey`로 저장한다.
- `:54-67` `readKey()` — `SecItemCopyMatching`이 `errSecSuccess`가 아니면 이유와 관계없이 `nil`. 사용자가 창을 거부·취소한 경우(`errSecAuthFailed` 등)도 "키가 없음"과 같게 취급한다.
- `:69-85` `saveKey()` — 먼저 `SecItemUpdate`, 항목이 없을 때만 `SecItemAdd`. 갱신에 `kSecAttrAccessible`을 넣는다.

빌드는 `build.sh`의 `codesign --force --sign -`(ad-hoc 서명)이라 **빌드마다 서명 해시가 달라진다.**
Keychain 항목의 허용 목록과 partition 목록은 이전 빌드의 서명을 기준으로 하므로, 새 빌드는 항상 허용 창을 거친다.

## 5. 영향

- 앱은 실행 중이고 직접 연결과 릴레이 연결도 있지만, 상대가 새 ID를 모르는 기기로 보아 입력·세션 메시지를 모두 무시한다.
  상대는 자기 변경도 보내지 않으므로 로컬에는 아무것도 반영되지 않는다.
- 릴레이 토픽은 두 Mac의 공유 비밀에서 유도되므로 ID(키)가 바뀌면 릴레이도 같은 이유로 맞지 않는다.
- 사용자에게는 "앱이 켜져 있는데 동기화만 안 되는" 상태로 보인다. 원인을 알려 주는 표시가 없다.
- 설치할 때마다 같은 위험이 있다(서명이 바뀌는 모든 재빌드·재설치).

## 6. 해결 옵션

| 옵션 | 내용 | 장점 | 단점·주의 |
|---|---|---|---|
| **A. `loadOrCreate` 수정 (권장)** | `errSecItemNotFound`일 때만 새 키를 만든다. 인증 실패·사용자 취소·상호작용 불가는 **기존 키를 건드리지 않고** `nil`을 돌려주고, 앱이 안내(또는 재시도)한다 | 조용한 신원 교체를 막는다. 정책 결정이 필요 없음 | 키 접근 함수를 주입 가능하게 바꿔야 단위 테스트가 가능함. 읽기 실패 때 앱이 어떻게 동작할지(동기화 중지 + 안내) 정해야 함 |
| B. 서명 정체성 고정 | ad-hoc 대신 재빌드해도 바뀌지 않는 인증서로 서명해 재설치 때 허용 창이 뜨지 않게 한다 | 설치 절차가 단순해짐 | 인증서 관리가 필요함. 이 방식에서 partition 목록이 어떻게 처리되는지는 **확인하지 않았다** |
| C. 설치 절차 안내 | `install.sh`와 README에 "Keychain 창이 뜨면 모두 승인해야 신원이 유지된다"를 명시 | 즉시 가능 | 사람이 지켜야 하는 절차라 실수를 막지 못함 |
| D. 복구 안내 | 신원이 바뀐 것을 감지하면 재페어링을 안내 | 증상 파악이 쉬워짐 | 상대 Mac의 신뢰 목록을 알 수 없어 이 Mac만으로는 감지가 어려움 |

## 7. 이번에 쓴 복구 방법

1. 앱을 종료하고 다시 연다.
2. Keychain 창이 뜨면 **모두 "항상 허용"으로 승인**한다. 암호를 요구하면 macOS 창에만 로그인 암호를 입력한다.
3. 로그 또는 Bonjour 이름 접미사로 ID가 유지되었는지 확인한다.
4. 상대 Mac이 새 ID를 신뢰하도록 재페어링한다(자동으로 찾기 또는 초대 코드).

## 8. 수락 기준

- [ ] 사용자가 Keychain 창을 거부·취소해도 기존 키가 덮어써지지 않는다.
- [ ] 읽기 실패 때 앱이 "신원을 읽지 못했다"는 취지의 안내를 보여 준다(조용한 실패가 아니다).
- [ ] 항목이 정말 없을 때(첫 실행)는 새 키를 만든다.
- [ ] 위 세 경우(성공·항목 없음·접근 거부)에 대한 단위 테스트가 있다.
- [ ] 재설치 절차가 README 또는 `install.sh`에 안내되어 있다.

## 9. 아직 확인하지 못한 것

- 비밀키를 직접 비교하지 못해 "키가 새로 만들어졌다"는 결론은 로그·코드·상대 Mac의 기록에서 추론한 것이다.
- 2번째 창이 **거부**였는지 **취소**였는지는 로그로 구분하지 못했다.
- 이 Mac을 재부팅한 뒤 창이 다시 뜨는지 확인하지 않았다. 현재 설치본은 "항상 허용"으로 승인되어 뜨지 않을 것으로 예상한다.
- `-34018` 오류가 `saveKey`의 최종 결과에 영향을 주었는지는 확인하지 못했다. 신원이 존재했다는 사실만으로 저장이 성공했다고 추론했다.
- 원격 Mac에 새 빌드를 설치할 때 같은 일이 생기는지는 확인하지 않았다.
