# 이슈 04 — 초대 코드 페어링 중 "공용 릴레이가 요청을 거절했습니다(HTTP 429)" 창이 뜨고, 페어링은 이어서 완료된다

| 항목 | 내용 |
|---|---|
| 상태 | 일시적 현상으로 보임, 코드 개선 여지만 확인(미수정). 원인 요청은 특정하지 못함 |
| 발견 | 2026-11-06, 재페어링 중 사용자가 보고(스크린샷) |
| 종류 | 사용성 — 오류 창이 실제 실패보다 먼저, 과하게 뜸 / 공용 서버 요청 제한 |
| 심각도 | 낮음 — 이 건에서는 이후 "페어링 완료"까지 정상 진행 |
| 관련 | [진행 기록 05](../progress/05-installation-and-field-test.md), 이슈 [03](03-keychain-identity-reset-on-reinstall.md) |

## 1. 한 줄 요약

초대 코드 페어링은 공용 `ntfy.sh`로 메시지를 보낸다. `ntfy.sh`가 요청 제한(HTTP 429)으로 응답하면 오류 창이 뜬다.
코드는 같은 메시지를 3번 나눠 보내는데, **그중 하나라도 실패하면** 곧바로 오류 창을 띄워 나머지가 성공해도 창이 먼저 뜬다.

## 2. 확인한 사실

| # | 사실 | 확인 방법 |
|---|---|---|
| F1 | 창은 **구버전인 원격 Mac**에서 뜬 것이다. 창 문구가 업스트림의 옛 문구("**Tailscale에서** 자동으로 찾기를 사용하거나…")이고, 이 Mac에 설치된 새 빌드의 바이너리에는 새 문구("**같은 네트워크에서** …")만 있고 옛 문구는 없다 | **실측** — `grep -a`로 바이너리의 UTF-8 문자열 검색 |
| F2 | 이 브랜치는 `PairingRendezvous.swift`를 바꾸지 않았다. `RelayChannel.swift`에서 바뀐 것은 `publish(_:to:)`의 접근 수준 한 줄뿐이다 | **실측** — `git diff` (업스트림 `f2d471a` 대비) |
| F3 | 초대 코드 흐름은 메시지를 3번씩 보낸다(참가 시 0.4·2·6초, 승인 시 0·1.5·5초). 응답이 2xx가 아니면 `reportError`가 한 번만 호출되어 오류 창이 뜬다 | **코드** — `PairingRendezvous.swift:120`, `:139`, `:203-204`, `:208` |
| F4 | 릴레이 재구독은 응답 상태와 무관하게 끊긴 뒤 **고정 5초** 뒤에 다시 시도한다 | **코드** — `RelayChannel.swift:203` |
| F5 | ntfy 공식 문서: 요청 제한에 걸리면 HTTP 429를 돌려주고 알 수 있으면 `Retry-After` 헤더를 준다. 방문자는 IP로 식별하며(IPv4는 전체 주소, IPv6는 /64), 기본값은 요청 버킷 60개에 5초마다 1개씩 채워지고 구독은 30개까지다 | **문서** — https://docs.ntfy.sh/config/#rate-limiting (문서의 기본값이며 공용 `ntfy.sh`의 실제 설정은 확인하지 못함) |
| F6 | 새 앱의 릴레이 연결은 유휴·동기화 중에 거의 늘지 않았다. 150초 동안 한/영을 7번 전환하는 동안 수신 +332바이트, 송신 +191바이트 | **실측** — `netstat -anv` |

## 3. 원인 분석

- **429의 직접 원인:** 공용 서버가 요청 제한을 걸었다. 같은 공유기 뒤의 두 Mac은 공용 IP가 같아 한도를 함께 쓴다고 추론되지만, 문서가 NAT 경우를 직접 설명하지는 않는다.
- **어떤 요청이 한도를 소진했는지는 모른다.** 초대 코드 흐름 자체는 Mac당 몇 개 안 되는 요청이라(구독 1 + 전송 3 + 3), 그 전에 쓰인 요청(앱 재실행마다의 구독, 릴레이 전송, 연속 페어링 시도)이 합쳐졌을 가능성이 있다. 같은 IP의 다른 트래픽도 배제하지 못한다.
- **오류 창이 과한 이유(F3):** 중복 전송은 일부 실패를 견디려고 만든 장치인데, 첫 실패에서 창을 띄우므로 그 장점이 사용자에게 보이지 않는다.
- **재시도가 한도를 유지할 수 있다는 우려(F4):** 구독이 429로 끝나면 5초 뒤 다시 시도하고, 이는 문서의 보충 속도(5초에 1개)와 같다. 제한 중에는 보충된 요청을 계속 소비할 수 있다. 이것은 코드를 읽고 한 추정이며 **실제로 발생하는 것을 보지는 못했다.**

## 4. 영향

- 사용자는 실패한 것으로 오해해 같은 시도를 반복하게 되고, 반복은 한도를 더 소진한다.
- 이번에는 오류 창 뒤에도 페어링이 완료되었다.
- 구버전의 문구는 Tailscale을 안내해, 이 브랜치의 방향(Tailscale 자동 탐색 제거)과 맞지 않는다. 새 빌드에서는 문구를 바꿨다.

## 5. 개선 후보 (구현하지 않음)

| 후보 | 내용 |
|---|---|
| 오류 보고 조건 | 3번의 전송이 **모두** 실패했을 때만 창을 띄운다 |
| 백오프 | 429의 `Retry-After`가 있으면 그만큼, 없으면 지수적으로 기다린 뒤 다시 시도한다(릴레이 재구독 포함) |
| 안내 문구 | "잠시 뒤 다시 시도" 안내에 같은 네트워크라면 자동으로 찾기가 릴레이를 쓰지 않는다는 점을 덧붙인다(새 빌드는 이미 같은 네트워크 안내로 바꿈) |
| 서버 | 자체 ntfy 서버 지정 옵션 — 이번 범위 밖 |

## 6. 사용자 대처

1. 1분쯤 기다렸다가 다시 시도한다.
2. 같은 네트워크라면 초대 코드 대신 **자동으로 찾기**(Bonjour, 릴레이 불필요)를 쓴다.
3. 두 Mac에서 번갈아 연달아 시도하지 않고 한쪽에서만 시도한다.

## 7. 수락 기준

- [ ] 중복 전송 중 일부만 실패하고 페어링이 성공하면 오류 창이 뜨지 않는다.
- [ ] 모든 전송이 실패하면 원인(상태 코드)과 대처가 담긴 창이 한 번 뜬다.
- [ ] 429 응답에서 재시도 간격이 `Retry-After` 또는 백오프를 따른다.
- [ ] 위 동작에 대한 단위 테스트(전송 함수를 주입해 상태 코드별로 확인)가 있다.

## 8. 아직 확인하지 못한 것

- 공용 `ntfy.sh`의 실제 요청 제한 값, 그리고 이번에 한도를 소진한 요청이 무엇인지
- 같은 공용 IP를 쓰는 다른 트래픽의 영향
- 창이 뜬 시점에 어떤 요청이 429를 받았는지(요청 단위 로그가 없음)
- 구독이 429를 받을 때의 실제 재시도 동작(코드 추정만 있음)
